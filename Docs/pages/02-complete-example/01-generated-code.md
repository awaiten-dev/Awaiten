# What Awaiten generates

Awaiten does its work at build time. For every `[Container]` the source generator writes a plain C# file that wires the graph, and the compiler builds it with the rest of your project. Nothing is discovered or emitted at run time.

This page walks through that file for the coffee shop of the [complete example](./index.md), so you can see what runs when the shop serves an order. The excerpts come from the real generated file, simplified: the `global::` prefixes, the disposed checks and the guards against re-entrant builds are left out, and `// …` marks elided code.

:::note[Not a contract]
The generated `Root` and `Scope` types, the public constructors of `Root` and the members of the interfaces they implement are the public surface you program against (see the [runtime API](../12-reference/02-runtime-api.md)). Everything else, such as the names of resolver methods, fields and the dispatch table, is an implementation detail that changes between versions. Do not call or reflect over it.
:::

## Two nested types

The generator adds one file named after the container, `Awaiten.CoffeeShop.g.cs`. It completes your `static partial class CoffeeShop` with two nested types: `Scope`, which holds the resolution logic, and `Root`, which derives from it.

```csharp no-compile
// <auto-generated/>
static partial class CoffeeShop
{
    public sealed class Root : Scope, IAwaitenRoot
    {
        public Root() : this(null) { }

        public Root(IExternalResolver? externalResolver) : base(externalResolver) { }

        public Task InitializeAsync(CancellationToken cancellationToken = default) { /* … */ }
        public AwaitenResolvability GetResolvability(Type serviceType, object? key) { /* … */ }
        // the singleton resolvers …
    }

    public class Scope : IAwaitenScope, IAwaitenExternalResolverHost,
        IAwaitenResolver<Grinder>, IAwaitenResolver<MenuBoard>, IAwaitenResolver<Barista>, // …
        IAwaitenAsyncResolver<EspressoMachine>, // …
    {
        // Resolve, TryResolve, ResolveAsync with their Type and keyed overloads,
        // CreateScope, CreateScopeAsync, Dispose, DisposeAsync,
        // and the resolvers of the scoped and transient services …
    }
}
```

- `Root` is what `await using CoffeeShop.Root shop = new();` creates. It is the outermost [scope](../04-core-concepts/02-scopes.md), and it holds the singletons: the `EspressoMachine`, the `Grinder`, the milks, the syrups and the terminal.
- `Scope` is what `shop.CreateScope()` returns for each order. It holds that order's `Order`, `Tab` and `Barista`, and it reaches the singletons through the root.
- The `Root(IExternalResolver?)` constructor takes the resolver for [imported services](../07-hosting/02-external-services.mdx#providing-the-external-resolver). The coffee shop imports none.
- The scope implements `IAwaitenResolver<T>` for each service it resolves synchronously and `IAwaitenAsyncResolver<T>` for every service, async or not, so `Resolve<T>()` and `ResolveAsync<T>()` take a typed path without a lookup.

## One resolver per registration

Every registration gets a static resolver method, and a dependency is a direct call to the resolver of its registration. The constructor arguments are plain method calls that the compiler checks.

### A singleton

The `Grinder` is cached on the root. The resolver returns the cached instance without a lock and builds it under a lock the first time:

```csharp no-compile
internal static Grinder ResolveGrinder(Root __s)
{
    if (__s._grinder is not null)
    {
        return __s._grinder;
    }

    lock (__s.__gate)
    {
        if (__s._grinder is null)
        {
            __s._grinder = new Grinder();
        }
    }

    return __s._grinder;
}
```

The decorated terminal from the `PaymentModule` is a singleton of the same shape. Its resolver builds the decorator around the inner registration, so nothing can reach the bare `CardTerminal` as an `IPaymentTerminal`:

```csharp no-compile
__s._loggingTerminal = new LoggingTerminal(Root.ResolveCardTerminal(__s.__root));
```

The pre-built `MenuBoard` has no cache of its own. Its resolver returns the `Instance` member you named, and the root never disposes it:

```csharp no-compile
internal static MenuBoard ResolveMenuBoard(Root __s) => Menu;
```

### A scoped service

The `Tab` is cached on the scope that resolves it, so each order gets its own. Because the `Tab` is disposable, its resolver also adds it to the scope's list of disposables, which the scope tears down in reverse order when the order is done:

```csharp no-compile
internal static Tab ResolveTab(Scope __s)
{
    if (__s._tab is not null)
    {
        return __s._tab;
    }

    lock (__s.__gate)
    {
        if (__s._tab is null)
        {
            __s._tab = new Tab(ResolveOrder(__s));
            (__s.__disposables ??= new List<object>()).Add(__s._tab);
        }
    }

    return __s._tab;
}
```

### The barista and its relationships

The `Barista` is scoped too. Its constructor call shows how each [relationship](../06-resolution/02-relationships.md) and collection shape turns into plain code:

```csharp no-compile
__s._barista = new Barista(
    ResolveTab(__s),
    new Func<string, Task<Cup>>((a0) => ResolveCupAsync(__s, a0, default)),
    new Dictionary<string, IMilk> { ["Oat"] = Root.ResolveOatMilk(__s.__root), ["Whole"] = Root.ResolveWholeMilk(__s.__root) },
    new ISyrup[] { Root.ResolveVanillaSyrup(__s.__root), Root.ResolveCaramelSyrup(__s.__root) },
    Root.ResolveLoggingTerminal(__s.__root));
```

- The `Func<string, Task<Cup>>` is a lambda over the cup's resolver. The [runtime argument](../06-resolution/06-runtime-arguments.md) `size` arrives as `a0`.
- The [keyed dictionary](../06-resolution/04-keyed-dictionaries.md) of milks is a dictionary literal with one entry per key.
- The [collection](../06-resolution/03-collections.md) of syrups is an array in declaration order.

### A transient built by a factory

Each call of the barista's `Func` builds a new `Cup` through the `MakeCup` factory. The cup needs the async `EspressoMachine`, so its resolver is asynchronous and awaits the machine before it calls the factory:

```csharp no-compile
internal static async Task<Cup> ResolveCupAsync(Scope __s, string a0, CancellationToken cancellationToken)
{
    Cup created = MakeCup(
        await Root.ResolveEspressoMachineAsync(__s.__root, cancellationToken).ConfigureAwait(false),
        Root.ResolveGrinder(__s.__root),
        a0);
    return created;
}
```

## Async initialization

The `EspressoMachine` matches the `[AsyncInitializer<IWarmUp>]` convention, so it gets an asynchronous resolver instead. It caches the `Task` that builds and warms the machine, so `WarmUpAsync` runs once even when several callers resolve it at the same time. A task that failed or was canceled is not kept, so the next call tries again.

```csharp no-compile
internal static Task<EspressoMachine> ResolveEspressoMachineAsync(Root __s, CancellationToken cancellationToken)
{
    Task<EspressoMachine>? __cached = __s._espressoMachineAsyncTask;
    if (__cached is not null && !__cached.IsFaulted && !__cached.IsCanceled)
    {
        return __cached;
    }

    lock (__s.__gate)
    {
        // start CreateEspressoMachineAsync once and store its task in _espressoMachineAsyncTask …
    }

    async Task<EspressoMachine> CreateEspressoMachineAsync()
    {
        EspressoMachine created = new EspressoMachine();
        await ((IWarmUp)created).WarmUpAsync(cancellationToken).ConfigureAwait(false);
        return created;
    }
}
```

`shop.InitializeAsync()` at startup awaits the asynchronous resolver of every async singleton, in dependency order. In the coffee shop that is the machine alone:

```csharp no-compile
public Task InitializeAsync(CancellationToken cancellationToken = default)
{
    return Core();

    async Task Core()
    {
        await ResolveEspressoMachineAsync(this, cancellationToken).ConfigureAwait(false);
    }
}
```

In the strict default, an async-initialized service has no synchronous resolver at all, so no synchronous path can hand out a cold machine. That is why the barista takes its cups through a `Task`. Under `AsyncSafety.SyncAfterInit`, a synchronous resolver would wait for the asynchronous one. See [Async initialization](../04-core-concepts/03-async-initialization.md#relax-the-rule-when-you-need-to).

## How resolve by type finds a service

`order.Resolve<Barista>()` takes the typed path through `IAwaitenResolver<Barista>`. `Resolve(Type)`, `TryResolve(Type, …)` and the shapes without a typed implementation, such as `Func<Grinder>`, look the type up in a static table that the `Scope` builds once. Each entry maps a `Type` to the resolver that produces it, and the table also holds the shapes the container synthesizes over each service:

```csharp no-compile
static Scope()
{
    __Bucket[] __entries =
    {
        new __Bucket(typeof(Grinder), static __s => Root.ResolveGrinder(__s.__root), false),
        // …
        new __Bucket(typeof(Tab), static __s => ResolveTab(__s), false),
        new __Bucket(typeof(Barista), static __s => ResolveBarista(__s), false),
        // …
        new __Bucket(typeof(IPaymentTerminal), static __s => Root.ResolveLoggingTerminal(__s.__root), false),
        new __Bucket(typeof(Func<Grinder>), __R0, false),
        // …
        new __Bucket(typeof(Func<string, Task<Cup>>), __R33, false),
        // …
    };
    __buckets = __BuildBuckets(__entries);
}
```

Each shape that has no resolver of its own, such as `Func<Grinder>` or the `Func` the barista takes, gets a small helper (`__R0`, `__R33`) that the table points to, so the table and its helpers grow with the registrations. The lookup hashes the type into a bucket of a static array and compares the few `Type` instances in that bucket by identity, so finding a service costs a hash and a short scan, not a walk over every registration, and it needs no reflection.

`Resolve(Type)` throws an `InvalidOperationException` when the table has no entry. For a service the container has but withholds from that call, such as the `EspressoMachine` on a synchronous `Resolve`, the message names the fix.

## A container with errors

When the container has an error, the generator emits no wiring. The file then contains only a `Root` that implements `IAwaitenRoot` and throws on use, so your code still compiles and the build reports the actual `AWT` diagnostics instead of follow-up errors about a missing type:

```csharp no-compile
public object Resolve(Type serviceType) => throw new InvalidOperationException(
    "Awaiten: container 'CoffeeShop' has registration errors; see the build diagnostics (AWT1xx).");
```

`TryResolve` on it returns `false`, and `Dispose` does nothing. This is what you get at run time when an error is suppressed or lowered so that the build passes, as the [Diagnostics](../09-diagnostics.md) page explains.

## See the generated code

In Visual Studio, open the project in Solution Explorer and expand **Dependencies**, **Analyzers**, **Awaiten.SourceGenerators** and **Awaiten.SourceGenerators.AwaitenGenerator**. Go to Definition on `CoffeeShop.Root` opens the file too. Rider lists the files of source generators under the project's dependencies as well.

To keep the files on disk, for a code review or a diff between versions, set `EmitCompilerGeneratedFiles` in the project file:

```xml title="CoffeeShop.csproj"
<PropertyGroup>
  <EmitCompilerGeneratedFiles>true</EmitCompilerGeneratedFiles>
</PropertyGroup>
```

The compiler then writes them below the intermediate output, to `obj/<Configuration>/<TargetFramework>/generated/Awaiten.SourceGenerators/Awaiten.SourceGenerators.AwaitenGenerator/`. Set `CompilerGeneratedFilesOutputPath` to choose another folder. When that folder is inside the project, remove its files from compilation, because the generator already adds them:

```xml title="CoffeeShop.csproj"
<PropertyGroup>
  <EmitCompilerGeneratedFiles>true</EmitCompilerGeneratedFiles>
  <CompilerGeneratedFilesOutputPath>Generated</CompilerGeneratedFilesOutputPath>
</PropertyGroup>
<ItemGroup>
  <Compile Remove="$(CompilerGeneratedFilesOutputPath)/**/*.cs" />
</ItemGroup>
```

## What this gives you

- **No reflection.** The generated code constructs with `new`, calls the factories and hooks you named, and looks types up by identity with `typeof`. It never scans assemblies or creates types at run time. A [scan](../05-registration/07-scanning.md) is read from the compilation at build time.
- **Plain C#.** You can read, step through and set breakpoints in the generated file like in your own code.
- **Native AOT and trimming.** The generated code and the `Awaiten` library contain no reflection-based activation, which the repository verifies with a native AOT test project. The [MS.DI bridge](../07-hosting/01-msdi-bridge.md#native-aot) is reflection-free as well.
- **Every target framework.** The same file compiles for every framework Awaiten supports, .NET Framework 4.8 included, with the [language version](../01-getting-started.md#requirements) the requirements name.

A [module](../05-registration/08-modules/index.md) in another assembly can generate code too: a public, `partial` module emits the factories and handles a container in that other assembly needs. See [Shipping modules from a library](../05-registration/08-modules/01-library-modules.md).
